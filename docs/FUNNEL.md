# Telegram Funnel Tracking

AfterHour accounts that funnel traders into Telegram channels, how we track them, and how the data is served.

> **Data credit:** the flag list (`accounts.json`) is curated by [TelegramScammers.com](https://telegramscammers.com) and published there as open data (`/accounts.json`, `/accounts.csv`). AfterMath adds post-history analysis, passive Telegram recon, an MCP tool and a lookup page. All listings mean **flagged for investigation, not a finding of fraud.**

## What is served

| Surface | What it is |
|---|---|
| `https://ah.mphinance.com/scamcheck` | "Check before you join": paste a `t.me` link or AfterHour username, get a match or no match. Static page, reads `api/funnel.json` in the browser. |
| `https://ah.mphinance.com/api/funnel.json` | All flagged accounts with tier, shared-link clusters, posting stats. |
| MCP tool `get_funnel_accounts` | Same lookup for AI agents. Inputs: `username`, `telegram_link`, `tier`, `limit`. |
| `https://ah.mphinance.com/api/funnel-tickers.json` | Ranked tickers called out by flagged accounts and their channels (`ah_accounts`, `ah_posts`, `tg_channels`, `tg_posts`). MCP tool `get_funnel_tickers` (`limit`). |
| `https://ah.mphinance.com/api/funnel-calls.json` | 300 most recent parsed callouts from public channels, with scored `outcome` where available. Quoted results are channel claims; small sample. MCP tool `get_funnel_callouts` (`ticker`, `channel`, `action`, `limit`). |

| `https://ah.mphinance.com/scorecard` | Public scorecard page: what each called option contract did after the post (main view), options held to expiry (secondary) and forex/gold/index signals scored TP1 first versus SL first, pooled and per channel, with sample sizes and 95% ranges. Static page reading the JSON files below. |
| `https://ah.mphinance.com/api/funnel-option-paths.json` | The option price-path numbers (see `tg_option_paths.py` and `build_funnel_paths.py` below). MCP tool `get_funnel_scorecard` with `section=paths`. |
| `https://ah.mphinance.com/api/funnel-scorecard.json` | The scorecard numbers (options, fx, coverage funnels, sensitivity, assumptions, content timeline). MCP tool `get_funnel_scorecard` (`section` paths/options/fx/all, `channel`). |
| `https://ah.mphinance.com/api/funnel-fx-signals.json` | Every scored forex/gold/index signal with levels, outcome, R and the original post text (400 chars). |

Evidence tiers (set by TelegramScammers.com): `reported` single observation, `corroborated` shared Telegram link across accounts, `verified` proof captured and admin-checked.

## Pipeline

```bash
python3 pull_funnel_posts.py     # full post history per account -> data/telegram_funnel/<user>.json
python3 analyze_funnel.py        # cadence, ticker bait, copy-paste spam -> reports/analysis/funnel_accounts.{json,md}
python3 build_funnel.py          # accounts.json + post stats -> api/funnel.json (also run by build_github_pages.py)
python3 tg_recon.py              # passive Telegram previews -> data/telegram_funnel/recon.json
python3 tg_watch.py              # snapshot + diff over time (link rotation, dead channels, member jumps, new wallets) -> reports/analysis/funnel_watch.md; schedule daily
python3 tg_calls.py                # parse trade callouts (ticker, strike, side, expiry, entry, quoted result) from archived Telegram posts -> data/telegram_funnel/calls.jsonl, reports/analysis/funnel_calls.md (run by tg_watch)
python3 tg_outcomes.py             # score option callouts vs the real tape (Yahoo public daily/5m bars) -> data/telegram_funnel/outcomes.jsonl, reports/analysis/funnel_outcomes.md
python3 tg_fx_signals.py          # parse forex/gold/index signals (XAUUSD, US30, NAS100, FX pairs) and score them vs Yahoo 5m bars -> data/telegram_funnel/fx_signals.jsonl, fx_claims.jsonl, reports/analysis/fx_signals.md (also run daily by `scripts/run_watch.sh`, `timeout 1500`)
python3 build_funnel_scorecard.py  # outcomes.jsonl + calls.jsonl + fx_signals.jsonl + fx_claims.jsonl -> api/funnel-scorecard.json, api/funnel-fx-signals.json (stdlib; missing inputs degrade to empty sections; also run by build_github_pages.py)
python3 funnel_tickers.py          # tickers called out (AfterHour posts + archived Telegram posts) -> reports/analysis/funnel_tickers.md
python3 build_funnel_calls.py      # calls.jsonl + funnel_tickers.json + outcomes.jsonl -> api/funnel-calls.json, api/funnel-tickers.json (public channels only; also run by build_github_pages.py; missing inputs degrade to empty lists)
python3 tg_merge_archive.py <remote_posts_archive.jsonl>   # merge the server's post archive into the local one (idempotent), then rerun tg_calls.py
python3 render_recon.py          # recon.json -> reports/analysis/funnel_recon.html (PNG: screenshot at 1200px, 2x)
```

### `tg_recon.py` (passive, no login, no joining)
Fetches only the public web previews Telegram serves to anyone: `t.me/<handle>` (title, description, member count), `t.me/+<hash>` (same, for private invites without joining) and `t.me/s/<handle>` (recent public posts). Extracts operator fingerprints (wallets, PayPal and cashtag handles, emails, prices, cross-promoted `t.me` links, `@mentions`) and clusters channels by identical description copy or shared fingerprint. It never posts, never uses an account, and sleeps between requests.

- Invite hashes are **case-sensitive**. Always use the original-case links (`telegram_links`), never the lowercased `telegram_links_norm`, or Telegram returns a generic "invalid invite" page.
- A generic "You are invited to a group chat" page means the invite is invalid, revoked or truncated; the script marks it `alive: false`.
- `--reanalyze` re-runs filters and clustering on an existing output with no network.
- Stock tickers (`$SPY`) are filtered out of the cashtag fingerprint.

### `tg_watch.py` (change tracking)
Runs `tg_recon.py` plus a re-check of every flagged AfterHour profile, saves a timestamped snapshot under `data/telegram_funnel/snapshots/` (gitignored), diffs against the previous one, and archives new public posts (deduped) to `posts_archive.jsonl`. Flags: bio link rotated, account gone, channel dead or revived, member jump (100 or 10%), description rewritten, renamed, new wallets/prices/admins, new cross-promoted channels. `--no-fetch` re-diffs the two newest snapshots offline. Public channel history beyond the newest ~20 posts is not paged yet (`t.me/s/<handle>?before=<id>` would do it).

### `tg_calls.py` (callout extraction)
Offline, stdlib-only parser over `posts_archive.jsonl`. One record per ticker mention: `action` (open, close, mention), `kind` (option, stock, spread), option `side`/`strike`/`expiry`, `entry_price`, `exit_price`, `result_pct`, plus `parse_flags` and, for closes, `open_id`/`open_link` pointing at the earlier open from the same channel. Docstring in the script lists every flag.

- Formats handled: `$NFLX 70P @.02`, `Opened 10 $SPX 7790C 10/08 @ $7.71`, `$BRZE 16 OCT 26 $25 CALL $0.95`, `SPY 777C 0.47 Odte`, `$REPX 50 Call 10/16.35` (date then price), `6/12 $TGT 133c @.16`, `$ESNT BTO / OCT/08 / 65C e:0.70`, `Entry: $3.80`, `avg .30`, `@1.10 from 0.90`, `$3.25 -> $3.62`, `Exit ... @ $3.62 · +11%`, `13/10` (day first), `1DTE`, bare tickers glued to a contract (`HOOD 10/16 112C`), `XXX TRADE CALL` headlines, `SPXW` (stored as SPX).
- On an open, `@ x` is the entry; on a close it is the **exit** (`exit_price`), and `entry_price` is only set when the post states it (`Entry:`, `from`, arrow). Older output put the exit price in `entry_price`.
- Never becomes an open: recap lists (`TRADE RECAP`, `CLOSED TRADES`, daily recap lines, `Position update`), the `Trade Summary` tail, `price_update` lines (`7700C @ 11 from 5.1`), hindsight talk, `Up 55%` marks, TP/SL/Take/Stop lines, `close to ITM`, bare-cashtag lists. A `Closed ...` line beats a later `Opened: 10:17 AM` line.
- Multi-leg (`170/172.5C CDS`, `spread`) is `kind: spread` with `strike` null and `strikes` set; downstream scorers that only handle single legs should skip them.
- `result_pct` is attached only to the ticker's own text, with comma thousands (`+1,200%`) handled. Quoted results are the channel's own claims; winners dominate (survivorship), so measure outcomes against the real tape.
- Filter on `parse_flags` before scoring: at minimum drop `duplicate_echo`, `spread*`, `expiry_before_post`, `entry_implausible`, `posted_date_suspect`; treat `no_expiry` as unknown (not same-day) unless `expiry_0dte_tag` is present.
- Accuracy (hand-labelled posts in `tests/fixtures/tg_calls_gold.json`, run by `tests/test_tg_calls.py`): on a stratified 110-post sample the old parser scored precision/recall of 0.88/0.49 on entry price, 0.67/0.54 on action and 0.50/0.35 on result_pct; the current one is at or near 1.00 on all fields on the sample it was tuned on and 0.97+ recall on the later batches. Add a gold post whenever a new failure shows up.
- `tg_watch.py` walks 6 pages (120 posts) back per public channel each run so busy channels are not missed between daily runs; `tg_recon.py --post-pages N` controls depth.

### `tg_outcomes.py` (callouts vs the tape)
Scores option callouts from `calls.jsonl` against the underlying's real price, using Yahoo's public chart endpoint (daily bars, 5m bars for posts within 55 days; no key, read-only GETs). No option price history exists, so the headline is **hold-to-expiry intrinsic** value minus the channel's quoted entry premium. "Touched breakeven" is an optimistic upper bound, not P&L. Entry premiums are the channels' own unverifiable fills and slippage is ignored, which flatters them. Null expiry is not assumed 0DTE unless the parser tagged it; impossible quotes (premium far below the contract's intrinsic value at the best print of the post day, flag `entry_below_intrinsic`: mis-parsed strike such as 1750 read as 175, wrong ticker, replayed old post) are excluded because one such row scores as a 200x winner and swamps the mean; echoes (same trade reposted) are collapsed; pending, far-dated and implausible records are reported but not scored. The sample is small and covers a short window, and expiry-day moves dominate. Assumptions and parser caveats: `reports/analysis/funnel_outcomes.md`, `reports/analysis/outcomes_parser_notes.md`.

**UI gate:** `scamcheck` shows outcome rates ("Callouts vs the tape") only when the path-based `callouts.paths.n_scored` is 100 or more (falling back to the hold-to-expiry `callouts.outcomes.n_scored` if the path file is absent); below that it shows "Collecting data" with no percentages. `api/funnel.json` always carries the numbers. Wording stays "flagged for investigation, not a finding of fraud", with credit to TelegramScammers.com.

### `tg_fx_signals.py` (forex / gold / index signals vs the tape)
For channels that post structured signals (`Gold Sell Now 4388 - 4395 Sl: 4298 TP: 50/100PIPS`, `US30 BUY 52020 TP 52060 ... SL 51900`) rather than stock options, which `tg_calls.py` never parses. Channel-agnostic, stdlib only, read-only (Yahoo public chart GETs, serial, 0.45s apart, cached per day in `data/telegram_funnel/price_cache/fx_*`). Run `python3 tg_fx_signals.py`; `--no-fetch` uses the cache only; `--basis auto|const|none`, `--horizon-hours`, `--touch-hours`.

- **Parse**: instrument (GOLD/XAU/XAUUSD to XAUUSD, US30, NAS100, JP225, FX pairs, `XXX/USD` crypto pairs), side, entry (single, zone `a - b`, `a / b`, abbreviated `4348-46`, or none), SL, TP list in prices or pips. Emoji, math-bold letters, superscript TP numbers and label variants (`Sl`, `Stop`, `TP1`, `1st`, `1_TP`, `Take Profit 1 (TP1)`, `Targets:`) are normalised first. Pips: gold 1 pip = 0.10, indices 1 point, FX 0.0001 (JPY 0.01); flagged `tp_pips_assumed`. Known gap: "NFP sell limit" posts never name the instrument and are not parsed.
- **Gates (in order)**: signal-shaped, bulk timestamp (same channel and exact timestamp on 6 or more posts, same rule as `tg_calls.py`), repost dedupe (60 minutes, sliding), SL and TP present, inside Yahoo's ~60-day 5m window, bar at post time, typo check against the market price (entry/SL/TP1 more than 4% off, or outside 0.5x to 2x; stop farther than 1% of price), fill, 24h horizon of data.
- **Tape**: the symbol is chosen per instrument by validating candidates against the signals' own stated entries (median absolute gap, coverage gate). `XAUUSD=X` returns HTTP 404 on Yahoo, so gold uses `GC=F`, whose futures basis (about 30 dollars, shrinking) is estimated from the entries and added back (`auto`). Basis error is the largest uncertainty; the report has a sensitivity table.
- **Scoring**: market fill at the close of the 5m bar containing the post, or fill-on-touch within 4h when the market is not in the entry zone (+/- 0.25 R tolerance); the two variants are never pooled. SL beats TP inside one 5m bar (`ambiguous`). R = |fill - SL|; reported mean R exit@TP1 and exit@last TP, hit rates with Wilson CIs, MAE/MFE. No spread, slippage or break-even management.
- **Outputs**: `fx_signals.jsonl` (one row per signal-shaped post, scored or skipped with `skip_reason`), `fx_claims.jsonl` (channel follow-ups such as "Tp1 done", "+180 pips"; not yet joined to signals), `reports/analysis/fx_signals.md`.
- **Tests**: `python3 -m pytest tests/test_tg_fx_signals.py` (47 hand-labelled real posts in `tests/fixtures/tg_fx_gold.json` plus synthetic-bar scoring cases). Add a fixture post whenever a format fails.

### `/scorecard` and `build_funnel_scorecard.py` (public scoring)
Decision (owner, 2026-10-14): **all scoring results are public**, pooled and per channel, options and forex/gold/index. Nothing is hidden behind a sample-size gate; instead every rate carries its n and a Wilson 95% interval, rows under n=5 are flagged `small` (hidden by default on the page, always in the JSON), and the page prints the full methodology. Language stays neutral and statistical: analysis of public posts, "flagged for investigation, not a finding of fraud", credit https://telegramscammers.com, not advice.

How the numbers are computed (all from files, nothing hard-coded):
- **Options** (`outcomes.jsonl`, `calls.jsonl`): scored opens with a computable return. `win_rate` = intrinsic value at expiry above the channel's quoted entry premium, so the headline says "held to expiry". `median_return`, `mean_return` are percent of the quoted premium; `worthless_share` = expired with zero intrinsic. `n_distinct_contracts` counts contracts keyed on ticker, side, strike and expiry alone (the same contract posted on several days or by several channels counts once; stats under `pooled.distinct_contracts`); `n_contract_days` additionally splits by post day (older builds called this figure distinct contracts, 1,092 versus 1,000 on the 2026-10-14 data). `coverage_funnel` walks option open callouts through each exclusion flag, unknown expiry, other unscorable, same-day repeats, pending, scored. `by_dte_bucket` uses expiry date minus post date (UTC); `by_ticker` is the 15 most scored; `by_channel` lists every channel with a scored open plus its deduplicated quoted closes and their mean. `paired` joins each close that carries a quoted result to its earlier open through the parser's `open_id`; the primary figures use exact `contract` links, `paired.all_links` adds the looser ticker-day links. The paired comparison is early exit versus hold, two different trades, and is described that way.
- **FX/gold/index** (`fx_signals.jsonl`): `pooled` is the market-fill variant only. TP1 first = TP1 traded before the stop within 24h of the fill; SL first = the reverse; `tp2plus_rate` uses signals listing 2 or more targets; `mean_r_tp1`/`mean_r_last` are in R (stop distance = 1R); `breakeven_tp1_rate` = 1/(1 + average winning TP1 distance in R). The fill-on-touch variant is under `touch_variant` and never pooled. `pooled.concentration` records channel and instrument concentration, the number of same-day setup groups (a proxy for independent observations; the 60-minute repost collapse does not catch later reposts of one setup), the window length in days and a 95% range for mean R at TP1. On the 2026-10-14 data: 50 of 51 market-fill signals are one channel, 44 are gold, they fall in 31 setup groups over 30 days, and the mean R range (-0.45 to +0.04) includes zero, so the sign of mean R is not established and the result cannot be told apart from break-even (hit rate 51%, range 38% to 64%, against a 64% break-even rate). The FX window is about one month against four for options; the two are not equal-length samples. `weekly_by_channel` appears for channels with 30 or more scored signals. `sensitivity` is parsed from section 4c of `reports/analysis/fx_signals.md` (so run `tg_fx_signals.py` first); `range` is the spread across the shifted and constant-offset basis rows. The basis (futures to spot, about 30 dollars on gold) is fitted from the channels' own stated entries and is the largest uncertainty; the page states its range beside the headline.
- **Content timeline** (`fx.content_timeline`): per channel, first and last dates of recognised forex/gold/index signal posts versus stock/option posts, with bulk-dump groups (same channel and exact timestamp on 6 or more posts, taken from `calls.jsonl` and `fx_signals.jsonl` rows). Bulk posts have unknown original dates and are not used to date a switch; where all stock/option posts sit in bulk groups the page says the switch cannot be dated.
- **Sample-size policy**: n and a Wilson 95% interval beside every rate; `small` = n under 5 (options channels, FX instruments, FX channels); channels hidden by default below n=5 but never dropped from the JSON; weekly FX tables only for channels with 30 or more scored signals; touch-fill never pooled with market-fill.
- Only public channels appear (`/+hash` invite links are dropped). Unreviewed candidate accounts never reach any tracked or served file.

Auto-refresh: `scripts/run_watch.sh` runs `timeout 1500 python3 tg_fx_signals.py` and `python3 build_funnel_scorecard.py` after `build_funnel_calls.py` (each failure-tolerant) and publishes `funnel-scorecard.json` and `funnel-fx-signals.json` with the same validate-then-atomic-swap loop. Publish gate (per file, in `scripts/run_watch.sh`, tests in `tests/test_run_watch_gate.py`): the file must be newer than a stamp taken at the start of the run (a failed build cannot republish the committed copy that `git reset` leaves in `api/`), must be populated (scorecard: both halves), and must not shrink against the file already live (options n_scored and callout totals keep at least 80%, FX scored signals at least 50% because FX ages out of Yahoo's 60-day 5m window). `FORCE_PUBLISH=1` skips only the shrink check. The server's archive was once far smaller than the local one (3k versus 13.5k posts) and overwrote a good scorecard with n=252 and 3 FX signals; merge archives (see above) and seed the price cache before relying on a server run. `fx_signals.jsonl`, `fx_claims.jsonl` and `outcomes.jsonl` are untracked by design, so the scorecard numbers cannot be rebuilt from a clean clone, only from a checkout that has run the pipeline. The first server FX run has an empty price cache and may hit the 1500s timeout; later runs use the cache. Tests: `python3 -m pytest tests/test_build_funnel_scorecard.py`.

### `/signals` (callout feed page) and daily auto-publish
`signals/index.html` is a static page at https://ah.mphinance.com/signals reading `api/funnel-calls.json`: newest-first callouts (time in ET, channel, ticker, strike, side, expiry, entry, open or close), filters (ticker, channel, type, scored-only, repeat posts), a scored-at-expiry chip per option open, and the channel's own claimed result on closes. Repeat posts are hidden by default. The feed shows its `generated_at` stamp. Export CSV downloads the filtered rows. Win rates and returns use scored option opens only; empty cells mean none scored.
The Coolify cron (`scripts/run_watch.sh`, called by the server's `run_watch.sh` wrapper after it fast-forwards the checkout) runs `tg_watch.py`, `tg_outcomes.py`, `funnel_tickers.py`, `build_funnel_calls.py`, `tg_fx_signals.py` and `build_funnel_scorecard.py`, validates the four JSON files and atomically publishes `api/funnel-calls.json`, `api/funnel-tickers.json`, `api/funnel-scorecard.json` and `api/funnel-fx-signals.json` into `/home/mph/apps/ah-portal/api/`. It does not rebuild `api/funnel.json` (accounts, clusters, outcome summary); that still needs a manual `build_funnel.py` plus deploy.

### `tg_backfill.py` (one-off deep history)
Walks back up to `--pages` pages (20 posts each) of every public channel's `t.me/s/<handle>` preview and appends new posts to the archive, deduped by post id. The daily run only walks 6 pages, so a busy channel can lose posts between runs; run this after adding channels or after a gap, then `python3 tg_calls.py`. Serial, about 1 second per page. Note some channels re-post history in bulk (many posts sharing one exact timestamp); `tg_calls.py` flags those as `posted_date_suspect` and the scorers skip them.

### `tg_option_paths.py` and `build_funnel_paths.py` (what the contract did after the call)
Decision (owner, 2026-10-14): hold-to-expiry "will never work" for channels that call quick scalps, so the main option view judges each called-out contract by its own price path after the post. Hold-to-expiry stays on `/scorecard` as a clearly secondary section.

**Data.** `python3 tg_option_paths.py backfill` pulls Alpaca historical 5-minute option trade bars for the exact evaluation window of every call (nothing is time-critical, history can be fetched at any time) into `data/telegram_funnel/option_bars/<OCC symbol>.json` (gitignored, local only; SPX calls try `SPXW` then `SPX`). `capture` (Yahoo, current session only, bars vanish after expiry) is just a fallback; `scripts/run_capture.sh` exists but is NOT scheduled and the earlier 20:30 UTC server cron is gone. **Alpaca credentials stay local** in `.env_alpaca` (`ALPACA_API_KEY_ID=...`, `ALPACA_API_SECRET_KEY=...`, one `KEY=value` per line, gitignored via `.env*`); never copy them to the server, a file in the repo or a log. The server has no bars, so the option-path data is rebuilt locally and deployed by rsync.

**Windows and fill.** Calls posted during the regular session (9:30 to 16:00 ET) get the 30 minutes of 5-minute bars after the post. "Daily callouts" (before the open, after the close, weekends) get the whole next regular session. Fill = open of the first bar at or after the post (or the session open). No print within 15 minutes of the post (or the open) is "illiquid", unscorable. Repost echoes (`duplicate_echo`, `cross_channel_echo`) are collapsed before scoring.

**Rules.** Reported per call: peak (MFE), drawdown (MAE), end-of-window return, volume, and first-touch rules +50/-50 (the headline), +100/-50 and +30/-30 measured from the fill. A bar touching both levels counts as the stop. "Ended above the fill" = last close in the window above the fill, never called a win rate. Rows go to `option_paths.jsonl`; `--delay-bars N` fills N bars later and `tg_option_paths.score(delay_bars, write=False)` returns rows in-process.

**Assumptions and limits.** Bars are trade prints, not bid/ask: spread and slippage are not modelled (true results would be worse on wide-spread lottos). Alpaca's feed is indicative, so prints can be missing. About 18% of quoted entries sit more than 25% below the contract's actual price at the post (unfillable quotes); they are counted, not removed. A coarse DAY VIEW (contract daily bar) exists for calls with no 5-minute bars but is outside the headline.

**Published file.** `python3 build_funnel_paths.py` writes `api/funnel-option-paths.json` (stdlib; imports `tg_option_paths` for the 0/1/2/3-bar delay sensitivity, reusing the previous file's block when bars are missing, and leaving the previous file untouched when there is no input at all): coverage funnel, pooled intraday and daily blocks with Wilson ranges and the three rule tables, delay sensitivity, quoted-entry realism, liquidity, by channel (every channel with a scored call, `small` under n=25, hidden by default on the page), by ticker (top 15), by ET hour of the post, plus methodology and limitations text. Everything is computed from the rows; no figures are hard-coded. Tests: `python3 -m pytest tests/test_build_funnel_paths.py`.

**Order and deploy.** `python3 tg_option_paths.py backfill` (when new calls arrived), `python3 tg_option_paths.py score`, `python3 build_funnel_paths.py`, `python3 build_funnel.py` (scamcheck headline reads the path file), `python3 build_funnel_export.py` (adds a `path` object per scored option open to `api/funnel-calls-full.json` and `path_*` columns to the CSV, joined on post id plus contract because one post can carry several contracts), `python3 build_funnel_scorecard.py`. Then rsync only the touched files. The server cron (`scripts/run_watch.sh`) never publishes `funnel-option-paths.json`, and its gate refuses a `funnel-calls-full.json` whose `path_count` is lower than the live file's, because the server rebuilds that export from its thinner archive without bars. Path fields in the export therefore appear only when it is built locally.

## Gotchas
